# Positioning

## One-Line Pitch

Mainspring gives agent businesses a local-first runtime and control plane for work that must be approved, replayed, inspected, and sold.

## Longer Pitch

Most agent tooling stops at prompt orchestration. Mainspring focuses on what happens after the model suggests an action: mailbox dispatch, runtime control, tool execution, policy checks, approval receipts, traces, and replayable operator context.

That makes it a better fit for builders who need to run agents for real clients, real workspaces, and real consequences.

## Target Users

- Solo founders building the first paid agent offering
- Agencies operating multiple client workspaces
- Developers replacing closed hosted agent stacks with self-hosted components
- Internal operator teams that need audit-friendly automation

## Pain Points Mainspring Addresses

- Chat transcripts are not enough when tools can change files or execute commands
- Agent businesses need repeatable approval and review flows
- Local-first builders do not want to start with a hosted control plane
- Security claims are often vague right where the blast radius matters
- Product teams need cleaner separation between model reasoning and consequence handling

## Why Mainspring Exists

Because prompt engineering alone does not create a business-grade agent runtime. Once an agent can read, write, search, browse, or execute, the hard problem becomes control, traceability, replay, and policy.

## Current Differentiators

- Preserved mailbox and event-journal runtime spine
- TypeScript SDK and runtime in one repo
- Honest prototype console that does not pretend to be live transport
- Security docs that state current limits directly

## What Mainspring Is Not Yet

- a secure desktop secret store
- a hardened VM isolation platform
- a billing ledger
- a hosted SaaS control plane
- a polished desktop app package
